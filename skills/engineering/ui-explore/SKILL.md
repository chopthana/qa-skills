# Exploratory UI run

หาบั๊กที่ test case ไม่ครอบ เพราะไม่มีใครนึกถึง วิธีคือเล่นจริงในเบราว์เซอร์
แล้วเฝ้าดูสัญญาณว่าแอปพัง

**output คือ findings ไม่ใช่ spec** การ generate Playwright spec จากการสุ่มเล่น
จะได้ของ flaky ที่ไปทำ CI พัง ของที่ยืนยันแล้วค่อยส่งเข้า pipeline test case
ของโปรเจคเป็นขั้นแยก

## ก่อนเริ่ม — 3 อย่างที่ต้องรู้ ขาดข้อไหนให้ถาม

1. **URL + หน้าไหน** และ login ยังไง (ถ้าต้อง)
2. **env นี้คืออะไร** — `local` (ของตัวเอง) / `shared` (dev, QA, staging ที่คนอื่นใช้) /
   `production-like` (มีข้อมูลจริง) ข้อนี้ห้ามเดา ถ้าดูจาก URL ไม่ชัดให้ถาม
   เพราะมันกำหนดว่ากดอะไรได้
3. **งบ** — เวลาหรือจำนวนคลิกต่อหน้าจอ default: 1 หน้าจอ, ~40 action, 10 นาที
   ไม่มีงบ = เดินไม่จบ

ถ้ามี design handoff ของหน้านั้น (ดู `design-handoff-check`) ให้อ่านก่อน จะได้รู้ว่า
หน้านี้ *ควร* มี state อะไร แล้วเล่นให้ถึง state นั้นแทนการสุ่มมั่ว — สุ่มมั่วเจอ
แต่บั๊กตื้น

## กฎความปลอดภัย — mode ตาม env

| env | mode | ทำอะไรได้ |
| --- | --- | --- |
| `local` | write-allowed | กดได้ทุกอย่าง ยกเว้น destructive (ดูล่าง) |
| `shared` | **read-only (default)** | เฉพาะ action ที่ไม่เขียนข้อมูล |
| `production-like` | read-only, ห้ามปลด | เฉพาะ action ที่ไม่เขียนข้อมูล ตลอด |

`shared` ปลดเป็น write-allowed ได้ **เฉพาะเมื่อผู้ใช้สั่งในรอบนั้น** และต้องบอกก่อน
ว่าจะไปเขียนอะไร การอนุญาตรอบก่อนไม่ต่ออายุมารอบนี้

### แยกว่า action ไหนเขียนข้อมูล — ดูจากพฤติกรรม ไม่ใช่จากคำบนปุ่ม

label แปลไม่ได้ทุกภาษาและทุกโปรเจค ให้ตัดสินจากสัญญาณจริง:

- **เฝ้า network** ก่อนกด ถ้ากดแล้วยิง `POST` / `PUT` / `PATCH` / `DELETE`
  = เขียนข้อมูล ใน read-only mode ห้ามกดซ้ำ และบันทึกว่าข้ามเพราะอะไร
- **มี confirm dialog** = ตั้งใจให้คนคิดก่อน ถือว่าเขียนข้อมูล
- **อยู่ในฟอร์มและเป็นปุ่ม submit** = เขียนข้อมูล
- **upload file** = เขียนข้อมูล เสมอ
- `GET` + ไม่มี dialog = ปลอดภัย (filter, search, sort, paginate, เปิด/ปิด modal,
  เปลี่ยน tab, hover, keyboard navigation)

ใน read-only mode: ไปถึงปุ่มที่เขียนข้อมูลได้ **เปิด modal ของมันได้**
อ่าน validation ที่ขึ้นทันทีได้ แต่ไม่กดยืนยัน

### destructive — ไม่กด ไม่ว่า env ไหน

ลบข้อมูล, ลบ user, revoke สิทธิ์ตัวเอง, ปล่อย job ที่กลับไม่ได้, ส่งของออกนอก
ระบบ (ส่งเมล แจ้งเตือน เรียก external API) ถ้าคิดว่าต้องกดจริงเพื่อหาบั๊ก
ให้หยุดแล้วถามผู้ใช้ พร้อมบอกว่าจะเกิดอะไรขึ้น

## วิธีเล่น

วนรอบนี้ต่อหน้าจอ จนหมดงบ:

1. **อ่านหน้าเป็น text ก่อน** (accessibility tree) ให้เห็น control ทั้งหมด
   อย่าเดาจาก screenshot
2. **ไล่กว้างก่อนลึก** — กดทุก control ชั้นบนสุดให้ครบก่อนค่อยลงไปใน modal
   บั๊กตื้นเจอจากการกวาดกว้าง ไม่ใช่จากการมุดลึกจุดเดียว
3. **ที่ช่องกรอก ลองค่าขอบ** ไม่ใช่แค่ค่าปกติ — ว่าง, space เดียว, 0, ติดลบ,
   ยาวเกิน, ตัวเลขในช่องตัวอักษร, อักษรในช่องตัวเลข, วันที่ย้อนหลัง,
   ช่วงที่เริ่มหลังสิ้นสุด, อักขระพิเศษ, emoji, ข้อความ RTL
   **นี่คือที่เจอบั๊กเยอะที่สุด** เยอะกว่าการกดปุ่มเฉย ๆ
4. **ลองลำดับที่ test case ไม่เขียน** — กดค้นหาตอนยังไม่เลือกอะไร, ล้างค่าแล้ว
   ค้นซ้ำ, กดซ้ำเร็ว ๆ สองที, เปิด modal แล้วกด Esc, กด back ของเบราว์เซอร์
   กลางทาง, reload ตอนมีผลค้างอยู่, เปิด 2 แท็บแล้วทำสวนกัน
5. **ยุ่งกับ URL ตรง ๆ** — param ที่ไม่ valid, ค่าที่หลุดช่วง, หน้าที่เกินจำนวนจริง,
   ลบ param ที่จำเป็นออก
6. **เปลี่ยนขนาดจอ** — แคบลงจนตารางต้องเลื่อนแนวนอน ดูว่าอ่านค่าได้ครบไหม
7. **อ่าน string ทุกตัวที่ขึ้นจอเพื่อหา typo** ทุก state ที่เดินไปถึง ไม่ใช่แค่
   state แรก — ข้อความ error, empty state, tooltip, placeholder, หัวตาราง,
   label ใน modal คือที่ที่ typo รอดมานานที่สุด เพราะไม่มีใครเปิดดู (ดูหัวข้อถัดไป)

หลังทุก action เช็ค 5 สัญญาณ:

- **console** — error / uncaught / warning ที่ชี้ว่าพัง
- **network** — 4xx, 5xx, request ที่ค้างไม่จบ
- **สภาพหน้า** — loading ไม่หยุด, ปุ่มกดต่อไม่ได้, หน้าขาว, state ค้างที่ออกไม่ได้,
  ตัวเลขสรุปไม่ตรงกับแถวที่เห็น
- **ข้อความ error กว้าง ๆ** ที่ไม่บอกอะไร — บั๊กจริงมักซ่อนอยู่ใต้ข้อความแบบนี้
  ดู log ฝั่ง server ถ้าเข้าถึงได้ ก่อนสรุปว่าเป็น env
- **wording ที่เพิ่งขึ้นมา** — ข้อความใหม่ทุกข้อความที่ action นั้นทำให้โผล่
  ให้อ่านจริง ๆ ทีละตัว ไม่ใช่กวาดตาผ่าน

ถ้ามี design spec ให้เทียบเพิ่มด้วยว่า state ที่เจอตรงกับที่ออกแบบไว้ไหม

## typo — ไล่ทุก string ที่ขึ้นจอ

typo คือบั๊กที่ขึ้นจอให้คนใช้เห็นทุกวันแต่ไม่มีใคร raise เพราะ "ไม่ใช่เรื่องใหญ่"
มันผ่าน test case มาได้เพราะเคสเขียนว่า "แสดงข้อความ error" ไม่ได้เขียนข้อความ
เต็ม ๆ ไว้ให้เทียบ

**อ่านเป็น text ไม่ใช่ screenshot** แล้วไล่ทีละ string:

- **สระ/วรรณยุกต์เกินหรือขาด**, วรรณยุกต์ซ้อน, สระหายหนึ่งตัว — ตาเปล่าไม่เห็น
- **ตัวสะกดผิดที่ยังอ่านออก** — ตัวสะกดเสียงใกล้กัน (`น`/`ล`, `ร`/`ล`,
  `ศ`/`ษ`/`ส`), ตัวการันต์หาย
- **เว้นวรรคผิดที่** — เว้นหน้าเครื่องหมายวรรคตอน, ไม่เว้นหลัง comma, space
  ค้างท้าย, space คู่กลางประโยค, ไทยติดอังกฤษโดยไม่เว้น
- **อักษรข้ามภาษาที่หน้าตาเหมือนกัน** — `O`/`0`, `l`/`1`/`I`, Cyrillic `а`
  ในคำอังกฤษ, เลขไทยปนอารบิก
- **คำเดียวกันสะกดสองแบบในหน้าเดียว** หรือหัวตารางกับ label ในฟอร์มเรียกของ
  เดียวกันไม่เหมือนกัน — อย่างน้อยหนึ่งอันผิด
- **ตัวพิมพ์ใหญ่/เล็กไม่คงเส้นคงวา** ในคำเดียวกันคนละที่
- **ของที่ไม่ควรขึ้นจอ** — `TODO`, `xxx`, `Lorem`, `undefined`, `null`,
  `NaN`, `[object Object]`, key แปล (`common.button.save`) ที่หลุดมาเป็น label
- **หน่วยและเครื่องหมายที่หาย** — `%`, สกุลเงิน, จุดทศนิยม, ตัวคั่นหลักพัน
- **ข้อความถูกตัดกลางคำ** โดยไม่มี ellipsis หรือตัดจนความหมายเปลี่ยน

สองสตริงที่ *ควร* เหมือนกันแต่ไม่ equal ให้เทียบเป็น codepoint แล้วบอกว่าต่าง
ที่ตัวไหน — NBSP, zero-width, วรรณยุกต์ซ้อน render ออกมาเหมือนกันเป๊ะ

typo เป็น finding เต็มตัว ไม่ใช่หมายเหตุท้ายรายงาน แต่ **ที่มาของ "ควรเป็น" ต้อง
ชัด**: ตรงกับ design spec, ตรงกับหน้าอื่นในระบบเดียวกัน, หรือ "ผมอ่านว่าสะกดผิด"
ซึ่งข้อหลังนี้ไปอยู่กองคำถาม ไม่ใช่กองบั๊ก

## เมื่อเจอ finding

**บันทึกแล้วเดินต่อ** อย่าหยุดทั้งรอบเพราะเจอหนึ่งอัน ยกเว้นหน้าพังจนเล่นต่อไม่ได้

ต่อ finding เก็บ:
- **repro** — ลำดับ action จากหน้าเปล่าถึงจุดเกิด ละเอียดพอให้คนอื่นทำซ้ำได้
- **เจออะไร** vs **คาดว่าควรเป็นอะไร** พร้อมที่มาของ "ควรเป็น" (design spec,
  test case, หน้าอื่นที่ทำแบบนั้น, หรือ "เหตุผลของผมเอง" — บอกให้ชัดว่าอันไหน)
- **สัญญาณ** ที่จับได้ (console/network/สภาพหน้า) ยกข้อความจริงมา
- screenshot ตอนเกิด
- **ความมั่นใจ** — บั๊กจริง / น่าสงสัย / อาจเป็น env

**ยืนยันซ้ำก่อนรายงาน** ทำ repro อีกรอบจากหน้าเปล่า ถ้าซ้ำไม่ได้ ให้รายงานว่า
ซ้ำไม่ได้ ไม่ใช่ตัดออกเงียบ ๆ — intermittent คือบั๊กชนิดหนึ่ง

**ของที่ไม่สมเหตุสมผลแต่ไม่รู้ว่าผิด ให้ตั้งคำถามเสมอ ห้ามข้ามเงียบ ๆ และห้าม
เดาเจตนาคนออกแบบ** แยกสองอย่างนี้ให้ขาด: **บั๊ก** คือของที่ขัดกับที่มาที่ชี้ได้
(design spec, test case, หน้าอื่นในระบบที่ทำอีกแบบ) — **คำถาม** คือของที่ขัดกับ
สามัญสำนึกของเราเท่านั้น เช่น ปุ่มที่กดแล้วไม่มีอะไรเกิดขึ้นแต่ไม่มีสเปคบอกว่า
ควรเกิดอะไร, ตัวเลขสองที่บนหน้าเดียวกันที่ไม่น่าจะต่างกันได้, ลำดับ sort ที่ดูไม่
ออกว่าเรียงด้วยอะไร, คำที่อ่านไม่เข้าใจว่าหมายถึงอะไร เขียนเป็นคำถามประโยคเดียว
พร้อมสิ่งที่เห็น แล้วเดินต่อ **ห้ามยกคำถามขึ้นเป็นบั๊กเพื่อให้รายงานดูมีน้ำหนัก
และห้ามทิ้งคำถามเพราะกลัวถามเยอะ** คำถามที่ส่งถึงคนที่ตอบได้ มีค่ากว่าการเดา
ที่ถูกบ้างผิดบ้าง

**กันรายงานซ้ำ** fingerprint = หน้าจอ + ชนิด action + ชนิดสัญญาณ + รูปของข้อความ
(ตัดตัวเลข/id ออก) เจอ fingerprint เดิมให้เพิ่มตัวนับ ไม่ใช่เพิ่มรายการใหม่

## Output

**ไฟล์** ใน scratchpad ของ session (ไม่ใช่ใน repo) ชื่อ
`ui-explore-<หน้า>-<YYYY-MM-DD>.md` + screenshot ข้าง ๆ บอก path เต็มในแชท:

```markdown
# <หน้า> — exploratory run (<date>)
env: <local|shared|production-like> · mode: <read-only|write-allowed>
งบ: <n> action / <n> นาที · ใช้ไป: <n> action
Design spec: <path|url|ไม่มี>

## สรุป
บั๊กจริง N · น่าสงสัย N · อาจเป็น env N · typo N · คำถาม N · ข้ามเพราะ read-only N

## F1 — <หัวข้อหนึ่งบรรทัด> [บั๊กจริง]
repro: 1) … 2) … 3) …
เจอ: … / ควรเป็น: … (ที่มา: …)
สัญญาณ: `<ข้อความจริง>`
screenshot: <path>
ซ้ำได้: ใช่ (2/2)

## คำถาม (ไม่ชี้ว่าผิด แต่ดูไม่สมเหตุสมผล)
- Q1 <สิ่งที่เห็น> — สงสัยว่า <คำถามประโยคเดียว> → ถาม BA/UXUI

## ข้ามไป (read-only)
- <action> → ยิง POST <path> ต้องปลด mode ก่อน
```

**ในแชท** list finding ทั้งหมดเรียงตามความมั่นใจ + คำถามทั้งหมด + บอกว่าข้าม
อะไรไปเพราะ mode
ถ้าไม่เจออะไรเลย ให้พูดตรง ๆ ว่าไม่เจอ และ list ว่าเล่นอะไรไปแล้ว — "เล่นแล้วไม่เจอ"
เป็นผลที่ใช้ได้ **ห้ามปั้น finding ให้ดูมีผลงาน**

## ส่งต่อเป็น test case

ขั้นแยก ทำเมื่อผู้ใช้สั่ง: finding ที่ผู้ใช้ยืนยันแล้ว → เขียนเป็น test case ผ่าน
pipeline ของโปรเจคนั้น (`testcase-to-domain` / `cases-to-e2e` หรืออะไรที่โปรเจค
ใช้) **เฉพาะอันที่ repro ได้แน่นอน** อันที่ซ้ำไม่ได้ยังไม่พร้อมเป็น regression test

## ห้าม

- ห้ามแก้โค้ดแอปเพื่อทดสอบ หรือเพื่อให้บั๊กหาย
- ห้ามรันคำสั่งฝั่ง backend / seed data เพื่อสร้างเงื่อนไข — skill นี้เล่นผ่าน UI
  เงื่อนไขที่ UI ไปไม่ถึง ให้บอกว่าไปไม่ถึง
- ห้ามกด destructive action ไม่ว่า env ไหน
- ห้ามปลด read-only เอง
- ห้าม hardcode label, route หรือ wording ของโปรเจคใดลงใน skill นี้
- ห้ามรายงาน finding ที่ยังไม่ได้ลองซ้ำ โดยไม่บอกว่ายังไม่ได้ลองซ้ำ
- ห้ามอ่าน wording จาก screenshot แล้วรายงานว่าเป็น typo — อ่านเป็น text เสมอ
- ห้ามข้ามของที่ไม่สมเหตุสมผลเพราะไม่แน่ใจ — ไม่แน่ใจคือเหตุผลที่ต้องถาม
