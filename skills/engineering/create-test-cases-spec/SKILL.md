# QA Test Case From Spec

แปลง Screenshot ของฟีเจอร์ + เอกสาร Spec ให้กลายเป็นชุด Test Case ที่ผ่านการรีวิวทีละ Section แล้วส่งมอบผลลัพธ์เป็นรูปแบบพร้อม copy-paste ลง Excel โดยตรงในแชท (ไม่สร้างไฟล์ เว้นแต่ผู้ใช้ขอ)

ใช้ภาษาเดียวกับที่ผู้ใช้ใช้ในบทสนทนา ทุกขั้นตอนด้านล่างจบด้วย "ปรับแก้ตาม feedback" เสมอ — หมายความว่า: แสดงผลลัพธ์ ให้ผู้ใช้แก้ไข (พิมพ์ตรงๆ หรือผ่าน `/plannotator-last`) นำไปปรับแก้ แล้วแสดงสถานะล่าสุด**ทั้งหมด** อีกครั้ง (ไม่ใช่แค่ diff) ก่อนไปขั้นตอนถัดไป อย่าข้ามไปขั้นตอนถัดไปจนกว่าขั้นตอนปัจจุบันจะถูก confirm

## ขั้นตอนที่ 1: วิเคราะห์ Screenshot
อธิบาย UI แยกทีละส่วน — บอกว่าแต่ละ element ทำหน้าที่อะไร ไม่ใช่แค่บอกว่ามันเขียนว่าอะไร สังเกตจุดที่ดูเหมือนจะผิดปกติหรือไม่สอดคล้องกัน แต่อย่าด่วนสรุปว่าเป็น bug — Mockup แบบ static (Figma) มักมีข้อมูลตัวอย่างที่ไม่จำเป็นต้อง "ถูกต้อง"

## ขั้นตอนที่ 2: ปรับแก้การวิเคราะห์ Screenshot ตาม Feedback
นำคำแก้ไขจากผู้ใช้มาปรับ (label ผิด, ปุ่มขาดหาย, สมมติฐานผิดเรื่อง default ฯลฯ) แล้วสรุปความเข้าใจที่แก้ไขแล้วใหม่ ทำซ้ำจนผู้ใช้พร้อมไปต่อ **wording/ชื่อ field ที่ confirm ในขั้นตอนนี้ถือเป็นแหล่งอ้างอิงหลักของ terminology ตลอด skill นี้**

## ขั้นตอนที่ 3: ทำความเข้าใจ Spec
อ่านเอกสาร JTBD / Acceptance Criteria / Business Logic สรุป**หน้าที่**ของแต่ละส่วน ไม่ใช่แค่ list เนื้อหา — อธิบายว่ามันมีไว้เพื่ออะไร ไม่ใช่แค่บอกว่ามันเขียนว่าอะไร มองหาความขัดแย้งภายในตัวเอกสารเองอย่างตั้งใจ (เช่น ตาราง summary ที่ให้เลขไม่ตรงกับหัวข้อรายละเอียดในเอกสารเดียวกัน) แล้ว flag ออกมาให้เห็นชัดเจน — ห้ามเลือกตีความแบบใดแบบหนึ่งเงียบๆ แล้วเดินหน้าต่อ

**หาก wording ที่ใช้ใน Spec ไม่ตรงกับ wording ที่ยืนยันแล้วจาก UI ใน Step 1-2 ให้เชื่อ wording จาก UI เป็นหลักเสมอ และห้ามแก้ไข wording ที่ confirm ไว้แล้วจาก Step 1-2 ตาม Spec** — Spec อาจใช้คำที่ไม่ตรงกับ UI จริง 100% (เช่น ชื่อ field, ชื่อปุ่ม, ชื่อ label) ให้ยึด UI เป็นความจริงสูงสุดด้าน terminology เสมอ

ปรับแก้ตาม feedback แบบเดียวกับขั้นตอนที่ 2

## ขั้นตอนที่ 4: Map Spec เข้ากับ UI
ไล่เทียบ field/พฤติกรรมใน spec กับสิ่งที่เห็นจริงใน screenshot แยกประเภทแต่ละจุดเป็น:
- ✅ ตรงกัน
- ⚠️ ไม่ตรงกัน — ต้องขอ confirm จากผู้ใช้/BA
- ❓ ยืนยันไม่ได้จาก screenshot นิ่งภาพเดียว

อย่าตีความว่าทุกจุดที่ไม่ตรงกันคือ bug — ให้ถามก่อน ปรับแก้ตาม feedback แบบเดียวกับขั้นตอนที่ 2

ติดตาม "คำถามค้าง" จากขั้นตอนที่ 1–4 ทั้งหมดเป็น list ต่อเนื่อง ทำเครื่องหมายว่าแก้ไขแล้วเมื่อผู้ใช้ตอบ — ห้ามหยิบเรื่องที่ confirm แล้วมาถามซ้ำ และห้ามทำเรื่องที่ยังค้างอยู่ (TBC) หายไปเงียบๆ

## ขั้นตอนที่ 5: แตก Test Case ทีละ Section
แบ่งหน้าจอตาม Section ที่มันถูกจัดวางไว้จริง (เช่น "เงื่อนไขการค้นหา" กับ "ผลการค้นหา" — ให้ยึดตามโครงสร้างจริงของหน้าจอ ไม่ต้องคิดแบ่งเอง) แต่ละ Section ทำตาราง markdown คอลัมน์: **Scenario | Ref AC | Precondition | Steps | Expected Result**

ใส่ Negative Case และ Combination Edge Case **ตั้งแต่ draft แรก** ไม่ใช่มาเพิ่มทีหลัง เช่น สำหรับชุด toggle เกณฑ์: เปิดทั้งหมด, ปิดทั้งหมด, เปิดทีละตัวแยก, และผสมกัน 2-3 แบบ สำหรับ field ที่รับ text input ให้ใส่เคส invalid-length และ invalid-character ด้วยแม้ยังไม่รู้ error message ที่แน่นอน — ระบุเป็น **TBC** แทนการเดา

**Steps ต้องเขียนแบบเต็ม ห้ามย่อ**: ทุกเคสเขียน Steps ตั้งแต่ต้นทางจริง — Login → คลิกเมนู/เมนูย่อยที่เกี่ยวข้อง → นำทางไปหน้า/section ที่ต้องใช้ → แล้วค่อยต่อด้วย action หลักของเคสนั้น ไม่ใช่สรุปการนำทางไว้แค่ใน Precondition สั้นๆ แล้วให้ Steps เริ่มจาก action หลักเลย แม้ Steps จะซ้ำกับเคสอื่นในชุดเดียวกันเกือบทั้งหมดก็ต้องเขียนซ้ำให้ครบ ห้ามขาด ห้ามข้าม (Precondition ยังใช้บรรยาย state ของข้อมูล/ระบบก่อนเทสต์ได้ตามปกติ แต่ไม่ใช่ตัวแทนของ navigation steps)

แสดงทีละ Section ให้ approve ก่อนค่อยไป Section ถัดไป อย่า draft ทุก Section รวดเดียวก่อนที่ Section แรกจะถูก confirm

## ขั้นตอนที่ 6: รวม Test Case ทั้งหมด
รวมทุก Section เป็นชุดเดียว คงการแบ่งกลุ่มตาม Section ให้เห็นชัด แต่ **เลข Test Case ให้รันต่อเนื่องตลอดทั้งชุด** (ห้าม reset เลขใหม่ทุก Section) ปิดท้ายด้วย:
- จำนวนรวมแยกตาม Section และรวมทั้งหมด
- รายการที่ยังเป็น **TBC** / รอ BA-PO confirm

**กำหนด TC ID ในขั้นตอนนี้**: ตกลง prefix กับผู้ใช้ก่อนเริ่ม (ปกติมาจากชื่อฟีเจอร์/การ์ดที่กำลังทำ เช่นการ์ด `QAP-1041 Promo Code Settings` → prefix `PROMO-CODE`) ถ้าผู้ใช้ยังไม่บอก ให้ถามก่อนแตก Section แรกในขั้นตอนที่ 5 แล้วผูก running number 3 หลัก (zero-padded) ต่อท้ายตามลำดับเดียวกับเลข Test Case ด้านบน เป็นรูปแบบ `<PREFIX>-NNN` เช่น `PROMO-CODE-001`, `PROMO-CODE-002` ... **รันต่อเนื่องตลอดทั้งชุดไม่ reset ตาม Section** (เลขชุดเดียวกับที่ใช้ใน Section header ด้านบน ไม่ใช่เลขแยกต่อ Section) — TC ID นี้เป็นตัวอ้างอิงเดียวกันทั้งฝั่ง Excel (ขั้นตอนที่ 8) และไฟล์โปรเจกต์ (ขั้นตอนที่ 7)

## ขั้นตอนที่ 7: เขียนไฟล์อ้างอิง (เฉพาะเมื่อถูกขอเท่านั้น)
ขั้นตอนนี้**ไม่ใช่**ส่วนหนึ่งของ flow โดย default ให้เขียนไฟล์เฉพาะเมื่อผู้ใช้ขอชัดเจนเท่านั้น ถ้าไม่ได้ขอ ให้ข้ามขั้นตอนนี้ไป — ตารางที่รวมแล้วจากขั้นตอนที่ 6 คือผลลัพธ์สุดท้ายที่ต้องส่งมอบ

มี 2 ปลายทางที่ตกลงกันไว้กับผู้ใช้ ถ้ายังไม่ชัดว่าต้องการแบบไหน (หรือทั้งคู่) ให้ถามก่อนเขียน:

**A. ไฟล์ Excel ตามเทมเพลตของทีม** (ปลายทางหลัก) — **หาเทมเพลตกับโฟลเดอร์ปลายทางก่อน อย่าสมมติ path**: ถามผู้ใช้ว่าเทมเพลตอยู่ไหน หรือ `ls` โฟลเดอร์ที่เก็บ workbook ของ sprint ก่อน ๆ แล้วยึดตามนั้น จากนั้น `cp` เทมเพลตออกมาก่อนเสมอ **ห้ามเขียนทับเทมเพลตเด็ดขาด** แล้วเขียนข้อมูลลงไฟล์ copy ตั้งชื่อตาม pattern ที่อ่านได้จากไฟล์พี่น้องในโฟลเดอร์นั้น (ยืนยันเลขการ์ดกับชื่อการ์ดกับผู้ใช้ก่อนเขียน)

> **Worked example** — ทีมหนึ่งเก็บเทมเพลตไว้ที่ `<โฟลเดอร์ test case>/Test Case - Template.xlsx` เขียนผลลงโฟลเดอร์ย่อยต่อ sprint และตั้งชื่อตามรูปแบบ `Test Case - <TRACKER> - {CARD_NO} - {CARD_NAME}.xlsx` เช่น `Test Case - QAP - 1041 - [Catalog][Promo] ตั้งค่ารหัสโปรโมชัน.xlsx` — ให้อ่านของทีมตัวเอง อย่าลอกอันนี้ไปใช้

**layout ของเทมเพลตให้อ่านจากไฟล์จริงเสมอ** สิ่งที่ต้องดู: หัวตารางอยู่แถวไหน (มักไม่ใช่แถว 1), คอลัมน์เรียงยังไง, คอลัมน์ไหนมีสูตรหรือ dropdown ที่ต้องคงไว้, และ style ของแถวตัวอย่างที่ต้องคัดลอกไปทุกแถว

> **Worked example** — เทมเพลตของทีมเดียวกันนั้น: sheet `TestResult` หัวตารางแถว 4 ข้อมูลเริ่มแถว 5 มี 12 คอลัมน์ — **A** ลำดับ (สูตร `=IF(Bn="","",ROW()-4)`), **B** ประเภทการทดสอบ = `System Test`, **C** TC ID (Calibri 11 ตัวหนา), **D** หัวข้อ, **E** กรณีทดสอบและขั้นตอนการทดสอบ, **F** ผลการทดสอบที่คาดหวัง (D-F Calibri 10 + wrap + พื้น `#F9FAFB`), **G** สถานะ = `Waiting to test` (เขียนทับสูตรเดิม), **H** Tester และ **I** Test date เว้นว่าง, **J** หมายเหตุ (Segoe UI 10 — กรณีปกติราบรื่น / กรณีทางเลือก / กรณีผิดพลาด แล้วต่อด้วย Ref AC), **K** ระดับความสำคัญ (High/Medium/Low), **L** Remark for Pass with Condition เว้นว่าง

- คัดลอก style ของแถวตัวอย่างไปใช้กับทุกแถวข้อมูล และตั้งความสูงแถวเป็น auto (`height = None`) เพราะเนื้อหายาวกว่าความสูง default ของเทมเพลต
- รูปแบบเนื้อหาในคอลัมน์ steps และ expected เหมือนขั้นตอนที่ 8 ทุกอย่าง (Precondition เป็นบรรทัดแรก เว้น 1 บรรทัด แล้วตามด้วย step มีเลขกำกับ ขึ้นบรรทัดจริงในเซลล์)
- เขียนเสร็จต้อง validate ทุกครั้ง: โหลดไฟล์กลับมานับจำนวนแถวที่มี TC ID ให้ตรงกับขั้นตอนที่ 6 เป๊ะ, TC ID เรียงต่อเนื่องไม่ซ้ำไม่ขาด, ไม่มีเซลล์ steps/expected ที่ว่างหรือยังค้างคำว่า `TBC` และเทมเพลตต้นฉบับยังเปิดอ่านได้เหมือนเดิม

**ปลายทางที่ทีมเลิกใช้แล้ว ห้ามเขียนกลับไป** — ถ้า repo นั้นมีโฟลเดอร์ test case เก่าที่เลิกใช้ไปแล้ว (ผู้ใช้จะบอกเอง) ไฟล์เดิมในโฟลเดอร์นั้นอ่านเป็น context ได้ แต่ห้ามสร้างไฟล์ใหม่ ห้ามแก้ ห้ามลบ และไม่ต้องเสนอให้เขียนลงไปอีก

**B. ไฟล์เก็บไว้ใน PROJECT** (รูปแบบไฟล์ยังไม่ตัดสินตายตัว — YAML หรือ JSON แล้วแต่ project นั้นใช้อยู่จริง ตรวจก่อนเขียนเสมอ อย่าสมมติเอง) — **ห้ามรวมเป็นไฟล์เดียว** ให้ **แยกไฟล์ตาม Section** ตามรูปแบบการแบ่งไฟล์ที่มีอยู่แล้วในโปรเจกต์สำหรับฟีเจอร์นั้น (เช่นถ้ามี `<test-case root>/<feature>/upload.yaml`, `preview.yaml`, `calculate.yaml` ฯลฯ อยู่ก่อนแล้ว ให้สร้าง/อัปเดตไฟล์ใหม่ตามชื่อ section เดียวกัน 1 ไฟล์ต่อ 1 Section ไม่ใช่ไฟล์เดียวรวมทุก Section) ก่อนเขียนให้ `ls`/`grep` โฟลเดอร์ปลายทางดูไฟล์พี่น้องเสมอเพื่อยึดรูปแบบ field/key ที่มีอยู่จริง — ถ้ายังไม่มีไฟล์ตั้งต้นในโฟลเดอร์นั้นเลย (ฟีเจอร์ใหม่) ให้ถามผู้ใช้ว่าจะตั้งชื่อไฟล์/แบ่ง Section อย่างไรและจะใช้ YAML หรือ JSON ก่อนเขียน อย่าตัดสินใจเงียบๆ

**ห้ามขาดเคส**: หลังเขียน/อัปเดตไฟล์เสร็จ ต้อง `grep -c` (หรือเทียบเท่า) นับจำนวนเคสในแต่ละไฟล์ที่แก้ แล้วรวมยอดเทียบกับจำนวนที่ตกลงไว้ในขั้นตอนที่ 6 ให้ตรงกันเป๊ะทุกไฟล์ — ถ้าขาดหรือเกิน ต้องหาสาเหตุและแก้ก่อนแจ้งผู้ใช้ว่าเสร็จ ห้ามปัดตกว่า "น่าจะครบ" โดยไม่นับจริง

**เรียง ID ภายในไฟล์ให้ถูกต้อง**: ID ที่ใช้จริงในไฟล์ YAML/JSON (ไม่ใช่ TC ID ฝั่ง Excel) มักมี pattern ของตัวเอง เช่น `<PREFIX>-<SECTION>-NNN` — ให้รันต่อเนื่องไม่ซ้ำไม่ขาดภายในไฟล์นั้นตามลำดับเดียวกับที่เคสถูกเรียงในขั้นตอนที่ 6 (ลำดับเดียวกับ TC ID) ถ้าเป็นการอัปเดตไฟล์ที่มีเคสอยู่ก่อนแล้ว ต้องต่อเลขจากเคสสุดท้ายที่มีอยู่ ไม่ใช่เริ่มนับใหม่จาก 001 ทับของเดิม

## ขั้นตอนที่ 8: Format สำหรับ Copy-Paste Excel (ในแชทเท่านั้น ไม่สร้างไฟล์)
ห้ามสร้างไฟล์ใดๆ สำหรับขั้นตอนนี้ (ไม่มี `.tsv`, ไม่มี `.xlsx`) เว้นแต่ผู้ใช้ขอไฟล์จริงชัดเจน พฤติกรรม default คือ พิมพ์เนื้อหาพร้อม copy โดยตรงในข้อความแชท

Format: 4 คอลัมน์ต่อ 1 Test Case — **TC ID / หัวข้อ / กรณีทดสอบและขั้นตอนการทดสอบ / ผลการทดสอบที่คาดหวัง** (ตัด Ref AC ออก) คั่นด้วย Tab ไม่มีแถว Header 1 แถวต่อ 1 Test Case **เรียงตาม TC ID จากน้อยไปมากเสมอ** (เลขเดียวกับลำดับ Section ที่รวมไว้ในขั้นตอนที่ 6 อยู่แล้ว จึงไม่ต้อง sort เพิ่ม แค่ห้ามสลับลำดับแถวเอง)

**TC ID**: ใช้ตามที่กำหนดไว้ในขั้นตอนที่ 6 (`<PREFIX>-NNN` เช่น `PROMO-CODE-001`) รันต่อเนื่องตลอดทั้งชุดไม่ reset ตาม Section — ต้องเป็น TC ID เดียวกับที่ใช้ในไฟล์โปรเจกต์ถ้าเขียนขั้นตอนที่ 7 (B) ด้วย

**หัวข้อ**: คือ Scenario เดิม

**กรณีทดสอบและขั้นตอนการทดสอบ**: คือ Precondition + Steps รวมกัน — รวมเข้าคอลัมน์นี้เป็น**บรรทัดแรกแบบมีคำกำกับ** รูปแบบ `Precondition (...)` ตามด้วยบรรทัดว่าง 1 บรรทัด แล้วค่อยตามด้วย Step ที่มีเลขกำกับ — **ห้ามเอา Precondition ไปแปะต่อท้าย Step 1 เป็นวงเล็บ** (เคยลองแล้วอ่านยาก โดยเฉพาะเคสที่ Precondition ซ้ำเนื้อหากับ Step 1 อยู่แล้ว เช่น Step 1 เป็น "ตรวจสอบว่า X มีสถานะ Y" กับ Precondition ที่บอกไว้แล้วว่า X สถานะ Y) ถ้า Precondition เป็น "-" หรือไม่มีเนื้อหา ให้ข้ามบรรทัดนี้ไปเลย เริ่มที่ "1. ..." ตรงๆ

**ผลการทดสอบที่คาดหวัง**: คือ Expected Result เดิม

แต่ละ Step และแต่ละข้อใน Expected Result ให้ขึ้นบรรทัดใหม่พร้อมเลขกำกับ ("1. ... / 2. ...") ภายใน cell เดียวกัน ครอบ cell ด้วยเครื่องหมายคำพูดคู่เมื่อมีมากกว่า 1 บรรทัด หรือมีเครื่องหมายคำพูดอยู่ในเนื้อหา และให้เครื่องหมายคำพูดภายในซ้อนเป็นคู่ (มาตรฐาน CSV/TSV escaping) เพื่อให้ paste ลง Excel/Sheets ได้ถูกต้อง

ตัวอย่าง 1 แถวในรูปแบบเป้าหมาย:

```
PMP-KPI-001	เข้าเมนูครั้งแรก ยังไม่เคยส่ง KPI มาก่อน	"Precondition (User A ยังไม่เคยมีเอกสาร PMS เลย)

1. เข้าสู่ระบบด้วย User A
2. Click เมนู ""KPI ของฉัน"""	"1. เข้าหน้า Landing ""KPI ของฉัน""
2. แสดง Empty State ตรงกลางหน้า: ไอคอนเอกสาร + แว่นขยาย + กากบาท สีเทา, หัวข้อ ""ไม่พบข้อมูล"", คำอธิบาย ""ไม่พบข้อมูลรายการ KPI โปรดดำเนินการสร้าง""
3. แสดงปุ่ม ""+ สร้าง KPI ใหม่"" มุมขวาบนของหน้า (นอกพื้นที่ Empty State)"
```

**วิธีสร้างและส่งมอบ**: จำนวน Test Case มักเยอะ (หลักสิบ) และมี field ที่มีเครื่องหมายคำพูดปนอยู่เยอะ (UI label) — อย่า escape เองด้วยมือ เสี่ยง error สูงเมื่อมีหลายสิบแถว ให้เขียน Python script (รันผ่าน Bash) parse ตารางที่ทำไว้ในขั้นตอนที่ 6 (หรืออ่านจากไฟล์ที่เขียนไว้ในขั้นตอนที่ 7) แล้ว generate TSV พร้อม escape ให้ถูกต้องอัตโนมัติ

**ห้ามใช้ Read tool แสดงไฟล์ผลลัพธ์ให้ผู้ใช้ดู** — Read tool เติมเลขบรรทัด (`1→`, `2→` ฯลฯ) นำหน้าทุกบรรทัด ซึ่งจะติดมาด้วยตอน user copy ทำให้ข้อมูลเสีย ใช้ Bash `cat` ตรวจสอบเนื้อหาได้ตามสบาย (ไม่เติมเลขบรรทัด) แต่**การส่งมอบจริงต้อง copy เนื้อหานั้นมาวางเป็น ``` code block ในข้อความตอบกลับโดยตรง** (ไม่ใช่แค่ปล่อยให้ user อ่านจาก tool output) — code block กด copy ง่ายกว่าข้อความธรรมดา ถ้าข้อมูลยาวเกินจะแสดงในครั้งเดียวไม่ไหว ให้แบ่งเป็นหลาย code block ตามแนวขอบ row (ห้ามตัดกลาง row ที่มี cell multi-line) และบอกผู้ใช้ชัดเจนว่านี่คือ "ส่วนที่ 1/2" ฯลฯ

ถ้าภายหลังผู้ใช้ขอไฟล์จริงแทนข้อความในแชท ให้ generate ด้วย Python: ใช้ module `csv` (delimiter=`\t`) สำหรับ `.tsv` หรือ `openpyxl` สำหรับ `.xlsx` จริง (Font Calibri 11 ทุก cell, `wrap_text=True` ที่คอลัมน์ Steps/Expected, ขึ้นบรรทัดจริง, ปรับความกว้าง column/ความสูง row อัตโนมัติ, ไม่มี Header) ต้อง validate ทุกครั้งหลังสร้างไฟล์ — parse `.tsv` กลับด้วย `csv.reader` แล้วเช็คว่าทุกแถวมี 4 field พอดี (รวม TC ID) และ TC ID ไม่ซ้ำ/ไม่ขาดตัวเลขระหว่างทาง หรือโหลด `.xlsx` กลับด้วย `openpyxl` แล้วเช็ค `font.name` / `alignment.wrap_text` ของ cell ตัวอย่าง — ก่อนแจ้งผู้ใช้ว่าเสร็จแล้ว
